Sesame: ESP32 quadruped walking robot

I built and tested a small quadruped robot based on the open-source Sesame project. The robot combines a 3D-printed frame, eight servo actuators and an OLED face in a compact platform for experimenting with legged movement and embedded control.

Motion planning for robotic tube-to-tubesheet welding

In shell-and-tube heat exchangers, each tube is welded to the tubesheet. The weld is a common point of failure, and the work is slow, repetitive and needs skilled welders. I built a motion plan in simulation that lets a 7-axis arm weld every tube in a tubesheet from three inputs.

What went wrong first

My first attempt fixed a welding torch model to the xArm7's flange. MoveIt could not plan the continuous 360° orbit around a tube: plans failed or the arm moved erratically.

What I changed

  • Designed a three-link end effector in SolidWorks: a link on the flange, a second link on a prismatic joint, and a torch link on a revolute joint.
  • Exported it to URDF and merged it with the xArm7 model. I built a MoveIt package with separate arm and tool planning groups.
  • Simulated the system in Gazebo, with joint goals sent to the controllers and joint states fed back to MoveIt.
  • Wrote Python with the MoveIt interface to set joint-state and pose goals.

How it works

The program takes the tube diameter, the joint type (flush or protruding) and the 3D centre of each tube. It orients the tool for the joint type, moves to each tube, rotates the flange to trace the weld, and flips the rotation direction on every other tube. Then it returns to the home pose. For protruding tubes the torch sits at 45° and the prismatic joint is set with:

distance = d − x + y + z

d = tube outer diameter, x = second link length, y = flange radius, z = cos(torch angle) × third link length.

Limits and next steps

This was tested in simulation only, on a simplified tubesheet. I did not tackle time parameterisation of the motion. Next steps are the Descartes or Pilz planners for finer control, and moving the code from Python to C++.

Tomato leaf disease identification with transfer learning

Plant disease threatens food supply, and expert inspection does not scale. I compared four ImageNet-pretrained CNNs as base models for classifying tomato leaf images into eight diseases plus healthy leaves (9 classes, 256×256 images).

  • Split the data 85:15 into train and test, then 7:3 of the training set into train and validation. Kept colour images, since leaf colour matters for diagnosis.
  • Added a 1000-unit ReLU layer with batch normalisation, 20% dropout and a softmax output. Trained with SGD and an exponentially decaying learning rate from 0.1.
  • Ran 5 epochs per model, on a CPU only, to compare them fairly.
Base modelTraining timeResult

The lesson: a more complex network is not automatically better. InceptionV3 trained fastest, and EfficientNetB0 matched VGG16's training time with far higher accuracy. I also saw overfitting in ResNet50 and EfficientNetB0, and would use more epochs, a GPU and deeper models such as ResNet152V2 next.

Smart welding helmet

Welders often work in confined, poorly ventilated spaces. This helmet monitors air quality, gas leakage and temperature around the welder and sends the data to the cloud, so the welder and a supervisor can both see it.

  • A Raspberry Pi Pico reads an MQ-2 gas sensor, an MQ-135 air quality sensor and a TMP36 temperature sensor. The sensors and board sit in 3D-printed cases adapted from Thingiverse designs.
  • Readings upload to a ThingSpeak channel every 20 seconds (the free-tier limit). The welder views them in the ThingShow Android app, and supervisors in a browser.
  • Alerts need no code on the microcontroller. A ThingSpeak React rule fires when values go out of range, calls a ThingHTTP request, and IFTTT pushes a notification to the phone.

It currently runs tethered to a computer, and the low-cost sensors are not accurate enough for industrial use. Next steps are a Li-Po battery version and better-calibrated sensors.
